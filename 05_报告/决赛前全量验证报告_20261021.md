#### 1. 雷达图空数据导致结果页崩溃

| 项 | 内容 |
|---|---|
| **位置** | `app/static/index.html` → `showResult()` 中 ECharts radar 初始化 |
| **复现** | 查询任一只具备工商信息、六维全部 na（无数据）的主体；或用 `page.route` 拦截注入 `dimensions` 各项 `na:true` |
| **现象** | 控制台抛 `TypeError: Cannot read properties of undefined (reading 'push')`（栈落在 `echarts.min.js:45`），`showResult` 中断 → 结果页只渲染一半 + 弹窗报错 |
| **根因** | ECharts radar 的 `indicator` 数组为空 `[]` 时内部 `visualMap` 处理越界。实测 n=0 崩、n≥1 正常（`value` 含 null/undefined 反而不抛） |
| **影响** | 演示中评委若输入一家非上市小公司，六维多为 na → 页面必崩，且这是"最该展示降级优雅"的场景 |
| **修法** | 新增 `radarKeys` 先过滤 `na`/`null`，`labels.length < 3` 时**不初始化图表**，渲染占位文案「可用维度不足 3 个，无法构成雷达画像——这正是"综合评价依据不足"的判定口径」 |
| **验证** | `_audit_radar_fix.js`：0/1/2 维 → `canvas=0` 且显示占位；3/6 维 → `canvas=1`；全部 `错误=0` |

#### 2. 四个接口缺主体锚定，不存在的公司被评为「满分安全」

| 项 | 内容 |
|---|---|
| **位置** | `app/server.py`：`/api/report`、`/api/regreport`、`/api/disposal/suggest`、`/api/scenario/evaluate` |
| **复现** | `POST /api/query {"name":"随便编一个不存在的公司名"}`（不传 `source`，默认 auto）→ 返回 **200** 且 `total_score: 100.0`；同一名字打 `/api/query` 却正确返回 404 |
| **现象** | 4 个入口对不存在主体一律 200 + 100.0 分；`/api/disposal/suggest` 甚至输出「无需处置，保持监控」 |
| **根因** | auto 模式下 iFinD/Wind 对查不到的主体**优雅返回空 profile 而非抛错**，`rate_supplier` 对空 profile 因"无扣分项"给出满分。`/api/query` 有 `_has_subject_data()` 门，这 4 个入口漏加 |
| **影响** | ① 评委随手输入一家小公司 → 系统说"100 分、无需处置"，专业性质疑；② 监管报送接口同样错 |
| **修法** | 4 处统一加 `_has_subject_data(res.profile)` → 404；`report`/`regreport` 另补 `MultiCandidateError` → HTTP 300（原先 auto 多候选会 500） |
| **验证** | 5 个查询入口对不存在主体**全部 404**、对正常主体**全部 200** |

#### 3. 写入接口不校验台账，产生永久孤立数据

| 项 | 内容 |
|---|---|
| **位置** | `app/server.py`：`POST /api/servicelevel`、`/api/servicelevel/batch`、`/api/contract/register` |
| **复现** | `POST /api/servicelevel {"supplier_id":"S999","period":"2099-12","values":{"sys_availability":99.9}}` → **200 并落盘** |
| **现象** | `data/service_levels.json` 被写入 `S999` 键；`GET /api/servicelevel` 总览里**看不到**它（`build_overview` 按台账遍历），但删除又必须知道 ID 才能清 |
| **根因** | 原实现只校验正则 `^[A-Za-z0-9_-]{1,32}$`，未校验是否在台账中 |
| **影响** | 演示数据被永久污染；本次验证过程中就三次触发（`BAD` 键、`S999`、`S001` 空期） |
| **修法** | 新增 `_assert_roster_id(sid)` → 不在台账返回 **404**「台账中不存在供应商 ID「S999」，请先在供应商台账中登记该主体。」，三处写接口统一调用 |
| **验证** | `S999` 三接口全 404；`S001` 全 200；S001 既有 6 期数据完整未损 |

### P1 · 口径错误 / 安全与稳定性风险（4 项，已修复）

#### 4. `constraints` 把「数据不足」误标为「信号升级」

| 项 | 内容 |
|---|---|
| **位置** | `static/index.html`（结果页徽标）与 `core/report.py`（导出报告） |
| **复现** | 构造仅 1 个维度有数据的 profile，触发 `insufficient` 约束 |
| **现象** | 页面显示「**信号升级**：出现恶化信号，等级不得判为正常」——把"数据不够"说成"经营恶化"；导出的 HTML 报告同样错 |
| **根因** | 前后端都做二元判断 `if type === "floor" ... else 信号升级`，而实际有 `floor`/`signal`/`insufficient` **三类** |
| **影响** | **业务口径错误**，直接损害专业性；且监管报送报告带同样错误 |
| **修法** | 前端 `CONS` 映射表 + 后端 `_CONS_META` 映射表，三类分别映射为「短板」/「信号升级」/「依据不足」 |
| **验证** | 前端 `_audit_ui_edge` C1 通过；报告 HTML 含「依据不足」且不含「信号升级」 |

#### 5. SSRF 守卫放行 CGNAT 网段

| 项 | 内容 |
|---|---|
| **位置** | `adapters/generic_adapter.py::_assert_public_url()` |
| **复现** | `POST /api/sources` 添加自定义源 `http://100.64.0.1/x` → **通过校验**（应拒绝） |
| **根因** | Python `ipaddress.IPv4Address("100.64.0.1").is_private` 返回 **False**（`100.64.0.0/10` 是 RFC 6598 运营商级 NAT，不在标准私有段内） |
| **影响** | 可被用作探测云厂商内部 CGNAT 网段的跳板 |
| **修法** | 单独定义 `_CGNAT_NET = ipaddress.ip_network("100.64.0.0/10")`，在逐 IP 校验循环内显式判断 |
| **验证** | `100.64.0.1` 拒绝、边界 `100.127.255.254` 拒绝、`100.128.0.1` 放行、`api.deepseek.com` 放行 |

#### 6. LLM 调用无超时，可能拖死请求

| 项 | 内容 |
|---|---|
| **位置** | `llm/deepseek.py` |
| **复现** | 构造网络抖动（或直接读代码） |
| **现象** | `OpenAI()` 未传 `timeout` → SDK 默认 **600s + 2 次重试**；`/api/query` 单次实测 3.8–10.7s，抖动时两次尝试可串到 20s+，叠加前端 150s 超时风险 |
| **修法** | `timeout=LLM_TIMEOUT_S(20)`、`max_retries=LLM_MAX_RETRIES(0)`，均可由环境变量覆盖 |
| **验证** | `/api/query` 稳定 4–12s，无挂死 |

## 三、遗留风险（6 项，已知且不阻塞演示）

1. **线上实时源凭据为空** → `available_source_keys()=[]` → auto 退化为纯本地快照（科蓝 78.57/yellow，本地 auto=77.79/red）。**用户已明确不改**。
2. **风险预警看板整页高 29,064 px**（186 条预警全平铺），缺分页/虚拟滚动。牵涉列表渲染与 E2E 断言，未动。
3. **4 个新模块零 E2E 覆盖**：`contract` / `alerts` / `roster_import` / `special_snapshot`。
4. **`/api/scan` 串行扫描首调 60.5 s**。可并行优化，但牵涉聚合器线程池语义，为避免引入竞态未改；前端超时 300 s 且仅按钮触发、提示"20–60 秒"，可接受。
5. **36 处正文块字号 11 px**（低于 11.5 px 阈值），视觉一致性小瑕疵。
6. **`core/alerts.py` 静态检查提示"持锁调用 `load_states`"** ——`_LOCK` 是 `threading.Lock` 非 RLock，但 `load_states` 本身不加锁，实测无死锁。

## 五、关键踩坑（供后续复用）

- ⚠️ **手工 curl 验证同样会把 `app/data` 写红**：即使写入内容与原值等价，`jsonstore.write_json` 输出 **LF** 而原文件是 **CRLF** → 语义相等、字节不同。验证后必须 `cp deploy/data/*.json app/data/` 还原。
- ⚠️ **门禁必须串行跑**：`verify_package.py` 内部以子进程调 `verify_security.py`，与另一个正在跑的验证脚本抢同一批端口/数据时会**偶发 FAIL**（本次实测出现过一次假失败，单独重跑即 13/13）。
- ⚠️ **审计脚本报 FAIL 先分清是谁的错**：本次 2 个 FAIL 里，`B6b` 是真缺陷，`G·单次查询` 是阈值设错。
